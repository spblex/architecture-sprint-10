# Выявленные проблемы и предложенные решения

CTO сформулировал две бизнес-потребности:
* Изменить парадигму хранения и учёта конфиденциальных данных. Она должна соответствовать принципам и требованиям законодательства РФ.
* Снизить риски утечки данных, чтобы увеличить доверие и лояльность клиентов.

Для реализации этих потребностей текущая архитектура должна эволюционировать в микросервисную. 
Поэтому во главе диаграммы Исикавы была поставлена цель "Эволюция архитектуры".

При анализе диаграммы Исикавы, выявленные проблемы можно обобщить сгруппировав следующим образом:

## Проблема 1: Незрелость процессов разработки

| Ключевые факторы      | Проблема                           |
|-----------------------|------------------------------------|
| Процессы              | Отсутствие процессов разработки    |
| Процессы              | Отсутствие процессов релиза        |

### Решение: 
1. Определить и описать все этапы разработки: 
   * анализ требований
   * разработка
   * тестирование 
   * релизный цикл
2. Для процесса разработки определить порог покрытия автоматическими тестами:
   * unit тесты
   * автоматические тесты
   * интеграционные тесты 
3. Внедрить в CI/CD пайп механизмы ИБ тестирования:
   * SAST
   * DAST 
4. Определить Контрольные точки для релиза и зафиксировать допущения: 
   * наличие документации к релизу
   * отчет о тестировании
   * порог допустимых багов в релизе по каждой критичности
   * прохождение НТ тестирования
   * отсутствие критических и высоких уязвимостей в отчете ИБ

## Проблема 2: Недостаточность компетенций

| Ключевые факторы      | Проблема                           |
|-----------------------|------------------------------------|
| Персонал              | Недостаточность компетенций        |
| Персонал              | Отсутствие команды разработки      |
| Управление            | СТО является разработчиком         |
| Управление            | Отсутствие лидеров компетенций     |

### Решение:
1. Выделить команду разработки по компетенциям:
   * Бэкенд разработка
   * Фронтенд разработка
   * Бизнес и системные аналитики
   * Команда тестирования
   * Команда автоматизаторов тестирования
   * Команда DevOps
   * ИБ специалисты
2. Внутри каждой компетенции выделить лидеров
3. СТО должен стоять во главе новой ИТ команды, но может также выполнять роль архитектора

## Проблема 3: Риски перехода на новую архитектуру

| Ключевые факторы      | Проблема                           |
|-----------------------|------------------------------------|
| ПО                    | Сложная миграция данных            |
| ПО                    | Необходимость реализации RBAC      |
| Интеграции            | Интеграции с внутренними системами |
| Интеграции            | Интеграции с внешними системами    |

### Решение:
До начала разработки:
   * составить целевую архитектуру
   * составить транзитивную архитектуру
   * провести сисемную аналитику:
     * описать процесс миграции данных 
     * описать мапинг структур данных
     * описать имеющееся АПИ
     * описать целевое АПИ
     * описать модель RBAC

## Проблема 4: Неготовность инфраструктуры

| Ключевые факторы      | Проблема                           |
|-----------------------|------------------------------------|
| Инфраструктура        | Отсутствие стендов разработки      |
| Инфраструктура        | Отсутствие CI/CD                   |

### Решение:
1. Развернуть стенды разработки:
   * DEV
   * TEST
   * ИФТ (Интеграционное тестирование)
   * ПреПРОД (с обезличенными данными со среды ПРОД)
   * ПРОД
2. Организовать процесс CI/CD:
   * git-подобная система хранения исходников
   * автоматическая сборка по коммиту
   * возможность деплоя на стенды разработки (DEV, TEST, ИФТ)
   * возможность деплоя на релизные стенды (ПреПРОД, ПРОД)
3. Повысить квалификацию текущего администратора системы
4. Оценить необходимость расширения команды DevOps
